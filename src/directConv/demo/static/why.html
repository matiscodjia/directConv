Why not just use numpy?

Both build the windows as a view.
Only one of them copies them.

The speed-up is not faster arithmetic. It is a copy that frugal_ml never makes, and that copy is most of numpy's time.

Where one frame's time goes

numpy

  1. sliding_window_view makes a strided view: no copy.
  2. np.tensordot hands it to a matrix product (BLAS), which needs one flat 2-D matrix.
  3. Flattening a strided view copies it: — per frame.
  4. Then a small matrix product: —.

frugal_ml

  1. im2col_view makes a strided view of the same kind: no copy.
  2. tensordot_3 takes the 6-D view as it is and reads it through its strides.
  3. Nothing is flattened, so nothing is copied.
  4. The multiply-adds run straight on the frame: —.

What it costs you

numpy pays for the copy once, whatever the number of filters. frugal_ml pays per filter and per channel, on one core, so its lead shrinks as the filter bank grows.

ChannelsFiltersnumpyfrugal_mlfrugal_ml vs numpy
  • The lab's workload is the first row (1 channel, 2 filters): the favourable end.
  • At 16 filters numpy catches up, because its matrix product reuses the one copy across all of them.
  • No BLAS, no threads: the loops are plain Rust, on one core.
  • Shapes are fixed when the program is built: a new frame size means a rebuild, which is what lets it run with no allocator.
